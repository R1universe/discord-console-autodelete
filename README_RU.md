# Discord AutoDelete v3.12 — инструкция (RU)

**Интерфейс по умолчанию — английский.** Это экспериментальный JavaScript, который работает в браузерной консоли Discord и автоматически пытается удалять новые сообщения текущего аккаунта по таймеру.

> **Риск:** Discord запрещает автоматизацию обычных пользовательских аккаунтов (self-bot). Возможна блокировка аккаунта. Не вводи и не пересылай токен, cookies или заголовки авторизации.

## Новое в v3.12 — стеклянный интерфейс Apple × Discord

Оформление переработано по выбранным макетам: **полупрозрачное стекло**, размытие Discord за панелью, объёмные кнопки и мягкие блики. Когда автоудаление выключено, панель подсвечена холодным **Blurple**; когда включено — мягким **Emerald**. Реальный эффект прозрачности зависит от браузера и фона под панелью.

- У карточек **Queued / Requests / Errors нет иконок**: только крупное число и подпись.
- Минимальная задержка теперь **1 секунда** вместо 2; максимальная — 86400 секунд (24 часа).
- Для серверов и DM по-прежнему раздельные таймеры и три равные по ширине настройки: **ручной ввод / 4s / 60s**.
- Важно: 1 секунда означает таймер *попытки* удаления после появления подтверждённого сообщения. Discord, ограничение скорости запросов и браузер могут увеличить фактическое время; удаление не гарантировано.
- Механизм обнаружения и удаления сообщений, фильтрация предварительных сообщений, настройки области и отмена очереди через Disable остались прежними.
- **Requests** — количество вызовов удаления, не подтверждённые успешные удаления. **Errors** — перехваченные ошибки, а не вся сетевая статистика.
- Это по-прежнему неофициальная автоматизация аккаунта, запрещённая Discord и потенциально приводящая к блокировке.

Автоматические тесты прошли, включая оба таймера в 1000 мс. Новый визуальный стиль ещё нужно оценить в реальном Discord Web. [Спецификация дизайна v3.12](./design/UX_SPEC_v3.12.md).

## Новое в v3.11 — симметричные таймеры и чистый заголовок

Убраны подзаголовок **Timed Discord messages** и кнопка **?** из заголовка. Диагностика остаётся доступной через раскрывающийся раздел **Diagnostics** внизу панели или команду `DiscordAutoDelete.openDiagnostics()`.

В каждой строке DM и Servers теперь **ровно три одинаковых по ширине элемента**: **ручной ввод секунд | 4s | 60s**. Ручной ввод по-прежнему поддерживает целые значения от **2 до 86400 секунд**; сохранение по Enter или потере фокуса. Сохранённые задержки из прошлых версий не сбрасываются, даже если не совпадают с новыми пресетами.

При выборе Everywhere видны оба таймера, при DMs или Servers — только соответствующий. Изменения касаются разметки и пресетов; механизм удаления и связанные риски self-bot не менялись. Автоматические тесты пройдены, визуальная проверка v3.11 на реальном Discord Web пока не выполнена.

## Новое в v3.10 — глубокая чёрная, «стеклянная» тема

Интерфейс стал более похожим на Discord, но с современной эстетикой: глубокий графит, мягкие полупрозрачные градиенты, тонкие бордюры, слегка светящиеся кнопки и единый переключатель Everywhere / Servers / DMs. При **Enable** акцент становится зелёным, при **Disable** — приглушённым сине-фиолетовым.

- Названия трёх счётчиков: **Queued / Requests / Errors**.
- **Requests** считает попытки вызова удаления, а **не подтверждённые удаления**.
- **Errors** считает ошибки, перехваченные скриптом; фоновые HTTP 404/429 могут не учитываться. Это ещё не исправлено — [Issue #2](./issues/2).
- Два длинных пояснения убраны из **Diagnostics**. Внутри остаются Activity Log и Reconnect. Краткое пояснение к счётчикам доступно по наведению.
- Предупреждение о риске self-bot не исчезло из документации: оно осталось в README и по-прежнему актуально.
- Логика очереди и удаления, независимые таймеры и условное отображение секций не изменялись.

Код прошёл автоматические тесты; отображение нового дизайна в Discord Web нужно проверить отдельно.

## Новое в v3.9 — выбор области определяет видимые таймеры

Теперь главный экран устроен так: **Enable / Disable → Where to delete → нужные таймеры → статистика**.

- Основная кнопка переименована: **Enable** при отключённом состоянии и **Disable** при включённом.
- **Disable**, как и прежняя Pause, **отменяет все ожидающие удаления**. Это поведение не изменилось.
- Переключатель **Where to delete** расположен сразу после кнопки Enable/Disable.
- При выборе **Everywhere** видны две настройки: сначала DM, затем Servers.
- При выборе **DMs** виден только таймер DM. При выборе **Servers** виден только таймер серверов.
- Скрытые значения сохраняются и восстанавливаются при возвращении к соответствующему режиму. Смена режима не пересчитывает запущенные таймеры: она влияет только на новые сообщения.
- Ручной ввод секунд, стили чёрно-зелёной темы, диагностика и механизм удаления не менялись.

Автотесты прошли, но новый интерфейс **ещё не проверен в реальном Discord Web**. Автоматизация обычного аккаунта остаётся неофициальной и запрещённой Discord.

## Новое в v3.7 — DM сверху и исправлен ручной ввод

Теперь **DMs · deletion delay** отображается **первым**, а **Servers · deletion delay** — вторым.

Раньше ввод чисел мог сбрасываться из-за автоматической перерисовки интерфейса каждые полсекунды. В v3.7 отдельное состояние редактирования защищает вводимые цифры от перезаписи, даже если Discord меняет фокус.

1. Кликни в числовое поле, выдели старое число и напиши новое (2–86400 секунд).
2. Нажми **Enter** или кликни вне поля — значение сохранится.
3. Нажми **Escape** для отмены изменения.

Во время печати можно временно оставить поле пустым или набрать однозначную цифру — проверка выполняется при сохранении. Если число недопустимо, возвращается прежнее значение. Быстрые пресеты и сохранение настроек не изменились.

Тесты имитируют ввод и перерисовку каждые 500 мс, но реальная работа v3.7 в твоём браузере **пока не проверена**.

## Новое в v3.5 — отдельные таймеры для серверов и DM

В интерфейсе появились две независимые настройки:

- **Servers · deletion delay** — задержка удаления твоих сообщений на серверах.
- **DMs · deletion delay** — задержка удаления твоих сообщений в личных и групповых DM.

Например, выстави **10 секунд для серверов** и **60 секунд для DM**, выбери **Everywhere: servers and DMs**, затем вручную включи AutoDelete. Программа определяет тип канала и ставит каждое новое сообщение в очередь со своим таймером. Если определить тип канала нельзя, сообщение пропускается, чтобы не применить неправильную настройку.

Каждая задержка поддерживает 2–86400 секунд и быстрые кнопки 5/10/30/60. Настройки сохраняются в браузере; после обновления страницы AutoDelete остаётся выключенным. При обновлении с v3.4 старая общая задержка используется как первоначальное значение **для обоих полей**. Изменение настройки не влияет на уже идущие таймеры.

Команды в консоли (необязательные):

```js
DiscordAutoDelete.setServerDelay(10) // только сервера
DiscordAutoDelete.setDmDelay(60)     // только DM
DiscordAutoDelete.setDelay(30)       // совместимость: оба таймера = 30с
DiscordAutoDelete.status()           // обе задержки и состояние
```

Новая версия прошла автоматические тесты на имитациях Discord, но **в реальном клиенте настройки независимых таймеров ещё не проверены**. Существующий риск блокировки аккаунта и ограничения API остаются.

## Что доказала диагностика 25 октября 2026 года

Версия v3.3 удаляла сообщения при пользовательских проверках, но **одно обычное отправление могло создавать две запланированные операции**. Отдельный скрипт [queue-audit.js](./diagnostics/queue-audit.js) показал:

- **M2:** предварительная версия сообщения (`id = nonce N1`), `state = SENDING`. Даже когда она находилась в кэше с `optimistic: false`, это ещё не было подтверждённое сервером сообщение.
- **M3:** настоящая подтверждённая версия с другим ID, но тем же `nonce N1`; в итоге `state = SENT`.

**В v3.4 исправлено именно это:** сообщения с `SENDING`, `optimistic: true` или `id === nonce` не ставятся на удаление. Подтверждённые события также группируются по `nonce`, чтобы не создавать две задачи на одно отправление. Тест GitHub Actions воспроизводит M2 → M3 и подтверждает ровно одну задачу.

**Важно:** v3.4 прошёл автоматические тесты на имитации Discord, но **в реальном клиенте пока не проверен**.

Счётчики теперь называются **Attempts** (количество вызовов удаления, а не подтверждённых удалений Discord) и **Caught** (перехваченные ошибки, но не все фоновые HTTP-отказы). Наблюдавшиеся ошибки 404 и 429 не обязательно попадут в Caught; этот вопрос отдельно отслеживается в [Issue #2](./issues/2).

## Быстрый запуск

1. Прочитай весь [autodelete.js](./autodelete.js), не запускай непроверенный код из случайных источников.
2. Открой [Discord Web](https://discord.com/app) и консоль браузера: на Mac в Chrome `Cmd + Option + J`.
3. Скопируй содержимое `autodelete.js` и вставь в Console. Никакого токена вводить не нужно.
4. В панели установи **две разные задержки**, для серверов и для DM: пресеты 5, 10, 30, 60 секунд или вручную 2–86400 секунд.
5. Выбери **Everywhere / Servers only / DMs only** и нажми **Enable auto-delete**.
6. Проверь работу на безобидном сообщении.

## Команды (необязательные)

```js
DiscordAutoDelete.status()        // состояние и мониторинг
DiscordAutoDelete.setDelay(30)    // общая команда: одинаковая задержка для обоих типов
DiscordAutoDelete.setServerDelay(10) // сервера
DiscordAutoDelete.setDmDelay(60)   // личные сообщения
DiscordAutoDelete.setScope("dm") // all, servers, dm
DiscordAutoDelete.pause()         // остановка и отмена очереди
DiscordAutoDelete.resume()        // включить
DiscordAutoDelete.retry()         // попытка переподключения
DiscordAutoDelete.stop()          // полное удаление панели
```

## Почему теперь другой способ подключения?

В предыдущих версиях код требовал конкретный `FluxDispatcher`, которого текущая сборка Discord не обнаруживала — ошибка `FluxDispatcher: 0 вариантов`.

В v3–v3.2:
- в v3.2 повторные экспорты одной функции удаления объединяются по **идентичности функции**, а не по количеству объектов-обёрток; при реально разных функциях удаление не запускается;
- поиск экспортов Webpack расширен, в v3.1 объединены модули нескольких runtime и добавлена проверка вложенного `HTTP` в экспорте с `getAPIBaseURL`;
- вместо `REST=false` теперь показывается количество кандидатов: ранее неоднозначность ошибочно выглядела как отсутствие модуля;
- у `FluxDispatcher` больше нет статуса обязательного компонента;
- резервный режим читает **MessageStore в текущем открытом канале** — это ограниченный режим, **не работает глобально во всех чатах**;
- удаление использует встроенный клиентский `RestAPI.del` (если найден) либо `MessageActions.deleteMessage`;
- при невозможности безопасного подключения **автоудаление остаётся выключенным**.

**Токен отдельно не требуется**, поскольку вызов выполняется внутри уже авторизованного Discord. Это не означает, что запросы не требуют авторизации — Discord использует текущую сессию.

## Ограничения

- В резервном режиме отслеживается только открытый канал; при переходах между каналами сообщения могут пропускаться.
- После перезагрузки страницы или закрытия вкладки скрипт прекращает работу, все таймеры теряются.
- Включение всегда ручное. Настройки задержки и области сохраняются в браузере.
- Сообщения, отправленные до включения, не удаляются; история чатов не сканируется.
- Собеседник или другой бот может сохранить сообщение до удаления.
- Отказ Discord API и лимиты запросов не гарантируют удаление ровно в срок.

### Диагностика v1.1

Первый отчёт просмотрел 52 606 объектов в двух Webpack-runtime и показал 83 стабильных `HTTP`-функции. **В диагностике v1.0 была ошибка:** она считала `HTTP` только когда свойство является функцией, хотя настоящий транспорт также может быть объектом. Поэтому из старого числа 83 нельзя сделать вывод о наличии 83 настоящих REST-клиентов Discord.

Новый [runtime-audit.js](./diagnostics/runtime-audit.js) (v1.1) выводит `httpPropertyTypes` и `crossFamily`. Он не отправляет запросы, не читает переписки, не извлекает токены и не вызывает команды удаления. Однако любое чтение JS-свойства теоретически способно вызвать его getter.

Чтобы скопировать **агрегированный JSON после запуска обновлённой диагностики**:

```js
copy(JSON.stringify(window.AutoDeleteAuditReport, null, 2))
```

Передавать нужно только этот отчёт, не содержимое вкладки Network или сведения об авторизации.


## v3.3 — вероятная первопричина найдена

Полный JSON диагностики v1.1 показывает **83 объекта, которые одновременно выглядят как пять разных компонентов Discord**. Это не похоже на реальные 83 независимых модуля удаления.

В [Vencord `shouldIgnoreValue`](https://github.com/Vendicated/Vencord/blob/main/src/webpack/webpack.ts) есть специальное исключение для `IntlMessagesProxy` и объектов, возвращающих значения на любой произвольный ключ. Некоторые Proxy кэшируют созданные при чтении функции, поэтому даже наличие собственного свойства и устойчивой ссылки на функцию не делает кандидата настоящим API.

**В v3.3 такие Proxy фильтруются до проверки методов.** В GitHub-тестах проверен случай с 83 имитированными переводческими Proxy и отдельным универсальным Proxy. Плюс исключён небезопасный перебор всех потенциальных event bus, когда настоящий Dispatcher нельзя выделить однозначно.

Как проверить:
1. Обновить страницу Discord Web (закрыть старые скрипты).
2. Вставить новый [autodelete.js](./autodelete.js).
3. Посмотреть, появился ли статус `PAUSED` вместо `ERROR`.
4. Выполнить `DiscordAutoDelete.status()`, проверить `filteredProxyExports` — сколько ложных экспортов отброшено.
5. Если подключение найдено, **включить вручную** и проверить на безобидном сообщении. При `Open-channel cache only` скрипт может видеть только текущий канал.

**Никогда не передавай токен, cookie или Authorization.** Автоматизация обычного аккаунта не разрешена Discord. Совместимость с реальным клиентом всё ещё требует проверки.

## Следующая ручная проверка версии 3.4

1. В собственном тестовом сервере выбери `Servers only` и задержку 60 секунд.
2. Отправь **одно** обычное тестовое сообщение.
3. Сразу проверь, показывает ли `Queued = 1` вместо `2`.
4. Нажми **Pause** до истечения таймера и убедись, что `Queued = 0`, а сообщение осталось. Это позволяет проверить очередь без дополнительных DELETE-запросов.
5. При желании позже проверь удаление ровно одного тестового сообщения, наблюдая реальные изменения в канале, а не полагаясь только на счётчики.

Не делай частые или массовые тесты: ранее Discord возвращал HTTP 429 (rate limit). Сам скрипт по-прежнему нарушает политику Discord.
