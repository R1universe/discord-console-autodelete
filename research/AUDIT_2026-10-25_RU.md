# Аудит Discord AutoDelete: 25 октября 2026

## Статус и метод

**Статус работающего автоудаления в реальном Discord: НЕ ПОДТВЕРЖДЁН.** Это исследование опирается на предоставленные скриншоты ошибки, исходники текущего репозитория и независимые реализации, указанные ниже. К аккаунту пользователя и его токену доступа нет; запросы DELETE на живом Discord не выполнялись.

Проверены три группы источников:

1. **Официальные Discord API / политика / rate limits**.
2. **Открытый код модифицированных клиентов**: Vencord, Guncord timeDelete, Moggcord SelfDestruct, Equicord.
3. **Программы удаления сообщений**: Undiscord, hddq/discord-messages-autodelete, Codefollows/discord-self-delete, Nanda070/SilentDelete, rmcord.

Этот обзор широкий по *архитектурам*, но не охватывает буквально все репозитории GitHub и весь интернет.

В отличие от пользовательского аккаунта, кандидат с подходящим методом ещё не подтверждает принадлежность настоящему HTTP-клиенту или системе сообщений.

## Основные системные ошибки

### 1. Поиск по именам методов — не верификация функциональности

Код считает подходящим любой экспорт `x`, где `typeof x.deleteMessage === "function"`, а затем пытается убрать неоднозначность. Так легко принять сторонние обёртки, прокси и несвязанные экспорты за `MessageActions`. Даже 84 разные ссылки на функции не означают 84 **семантически различных** операций.

**Гипотеза, требующая проверки:** необычайно близкие числа подходящих экспортов для `getCurrentUser`, `getMessages`, `del` и `deleteMessage` могут объясняться динамическими Proxy, ленивыми экспортами или универсальными обёртками. Их пересечение, стабильность повторного чтения метода и own-property характеристики можно проверить отдельно.

### 2. `wreq.c` — только уже инициализированные модули

В документации Vencord `wreq.c` — кэш выполненных модулей, `wreq.m` — доступные фабрики. Дополнительные chunks могут загружаться позднее. В нашем прототипе нет полноценного `waitFor`/lazy discovery, как в Vencord, и нельзя достоверно утверждать, что отсутствие подходящего экспорта означает отсутствие функциональности вообще.

Не рекомендуется бездумно вызывать `require` на каждом найденном module ID: исполнение модулей может иметь побочные эффекты и повредить клиент.

### 3. 24 кандидатных Dispatcher — не 24 действительных источника событий

Наш код подписывался на все найденные `subscribe + dispatch` кандидаты. Он не проверял, какой объект действительно получает события `MESSAGE_CREATE` после отправки собственного сообщения. В таком режиме можно получить ложное ощущение, что «подключение выполнено», хотя события из Gateway не поступают.

### 4. Неполнота резервного `MessageStore`-режима

Polling сообщений через `SelectedChannelStore` способен наблюдать **только открытый канал**; он не осуществляет непрерывную обработку всех серверов и всех DM. Переходы между каналами и быстрые сообщения можно пропустить. Этот резервный вариант не эквивалентен обещанному «везде, через X секунд».

### 5. Нет доказательства серверного удаления

Локальный метод `deleteMessage` может возвращать значение до подтверждения HTTP-результата. Статистика количества вызовов не эквивалентна количеству полученных подтверждений 204 или событий удаления. В текущем прототипе отсутствуют полноценные механизмы восстановления после 429, продолжение очереди после перезагрузки страницы и независимая проверка результата.

### 6. Подтверждённые ошибки интерфейса и фильтра

- v3.2 показывал «AutoDelete v3.1» в заголовке и «LOCAL v3.2.0» ниже. Исправлено в v3.2.1.
- В режиме «DMs only» условие `!guild && !channel` считало отсутствие метаданных доказательством DM, хотя это могло быть серверное сообщение с неполным событием. Исправлено на строгую проверку типа DM (fail closed).

### 7. Тесты имитировали модель, которую мы сами придумали

Проверки GitHub Actions доказывают работоспособность скрипта в определённой тестовой среде. Они не подтверждают актуальность частных интерфейсов Discord и не заменяют реальную интеграционную проверку.

## Нужен ли пользовательский токен?

- **Официальный API-бот:** отдельный bot token, разрешённый разработчикам, права в серверах; не удаляет сообщения обычного пользователя в приватных DM других людей.
- **Self-bot как внешнее приложение:** как правило, применяет токен пользовательского аккаунта; это особо чувствительный секрет и нарушение политики Discord.
- **Инъекция в уже авторизованный веб-клиент:** может вызывать внутренний авторизованный транспорт, если он доступен. Поэтому **отдельное извлечение токена не является обязательным**, но и нет гарантии, что нужная функция доступна консольному скрипту. Это всё равно неофициальная автоматизация.

Не нужно присылать или вставлять пользовательский токен, cookie, заголовок Authorization или приватные данные.

## Официальные источники

- [Discord Message API](https://discord.com/developers/docs/resources/message): DELETE endpoint, 204 на успешный запрос, права доступа.
- [Discord API Rate Limits](https://discord.com/developers/docs/topics/rate-limits): 429, Retry-After, ограничения на операции.
- [Self-bot policy](https://support.discord.com/hc/en-us/articles/115002192352-Automated-User-Accounts-Self-Bots): автоматизация обычных пользовательских аккаунтов запрещена.
- [Discord OAuth2 / bot users](https://discord.com/developers/docs/topics/oauth2): чем боты отличаются от пользовательских аккаунтов.

## Проверяемая диагностика: следующий шаг

Добавлен [diagnostics/runtime-audit.js](../diagnostics/runtime-audit.js). Это **отдельный скрипт только для чтения**. Он выводит агрегированные характеристики экспорта Webpack без обращения к сообщениям, имени пользователя, токену или сетевым запросам.

Предназначен для проверки:
- повторное чтение `obj.deleteMessage` возвращает одну и ту же функцию или новую;
- есть ли собственное свойство `deleteMessage` / `del`, или это динамическое обращение;
- сколько кандидатов одновременно выглядят как UserStore, MessageActions, REST и MessageStore;
- сколько модулей загружено (`c`) и сколько фабрик известно (`m`).

### Запуск

1. Сначала перезагрузить Discord Web, чтобы старый AutoDelete не исполнялся.
2. Открыть `diagnostics/runtime-audit.js` в GitHub и внимательно прочитать.
3. Вставить только диагностический JS в консоль Discord Web.
4. После выполнения появится `[AutoDelete Audit] Read-only, anonymous module report` и JSON.
5. При желании прислать только **агрегированный отчёт**; токен и приватные данные не присылать.

Этот отчёт позволит ответить на главный вопрос: являются ли 83–84 кандидата повторными или синтезированными обёртками, либо речь о разных реально существующих реализациях.

## Решение об архитектуре

**Не выпускать v3.3 с произвольным «первым подходящим» модулем.** Сначала выяснить происхождение ложных кандидатов. Если доступ к правильным API нестабилен, для поддерживаемого серверного сценария использовать официального Discord-бота. Если нужен именно обычный аккаунт в DM, нет поддерживаемого Discord метода; существующие self-bot/мод-реализации нарушают правила платформы и могут привести к блокировке.

Без реального интеграционного доказательства README и UX не должны обещать «работает везде».
